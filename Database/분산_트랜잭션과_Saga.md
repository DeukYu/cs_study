# 분산 트랜잭션과 Saga 패턴
> 📌 기출: [NC Project NL Q19, Q20, Q21](../Interview/NC_Project_NL_%EB%A9%B4%EC%A0%91_%EC%A7%88%EB%AC%B8.md) - 여러 서버가 서로 다른 DB를 사용할 때 트랜잭션 처리 / 재화 차감 후 아이템 지급 전 Crash 처리

- 서버마다 DB가 다르면 하나의 트랜잭션(ACID)으로 묶을 수 없습니다.
- 게임 거래소처럼 **재화 DB와 아이템 DB가 분리된 구조** 에서 정합성을 지키는 방법을 정리합니다.

---

## 2PC (Two-Phase Commit)
- 코디네이터가 모든 DB에 **Prepare → Commit** 두 단계로 커밋을 조율하는 방식 (MSSQL은 MSDTC)
- **잘 쓰지 않는 이유**
    - 모든 참여자의 응답을 기다리는 동안 락이 잡혀 성능이 나쁩니다.
    - 코디네이터 장애 시 참여자들이 락을 쥔 채 멈춥니다 (blocking).
    - 이기종 저장소(Redis 등)에는 적용하기 어렵습니다.

---

## Saga 패턴
- 큰 트랜잭션을 **로컬 트랜잭션 여러 개로 나누고**, 실패하면 앞 단계를 되돌리는 **보상 트랜잭션** 을 실행하는 방식
- 각 단계는 자기 DB 안에서만 원자적이고, 전체는 **최종 일관성 (Eventual Consistency)** 을 보장합니다.

### 거래소 구매 흐름 예시
```
Started ─▶ Reserved ─▶ Paid ─▶ Delivered ─▶ Completed
           (매물 예약)  (재화 차감) (아이템 지급)
              │            │
              ▼            ▼
          예약 해제      재화 환불      ← 실패 시 보상 트랜잭션
```

### 구현 원칙
1. **거래 로그 (상태 머신)**
    - 거래마다 고유 `TransactionID`를 발급하고, 거래 로그 테이블에 현재 상태를 기록합니다.
2. **변경과 기록을 같은 트랜잭션으로**
    - 각 단계는 그 DB의 로컬 트랜잭션 하나에서 "데이터 변경 + 해당 TransactionID 처리 기록"을 함께 커밋합니다. (Outbox / 처리 내역 테이블)
3. **멱등성 (Idempotency)**
    - `TransactionID`에 UNIQUE 제약을 걸어, 같은 요청이 재시도되어도 두 번 차감/지급되지 않게 합니다.
4. **Roll-forward 우선**
    - 재화가 나간 뒤에는 되돌리기보다 지급을 끝까지 완수하는 쪽을 우선합니다.
5. **복구 스캐너와 대조**
    - 미완료 거래는 주기적 배치가 찾아 재처리하고, 일정 횟수 실패하면 운영 알림 + 수동 처리로 넘깁니다.
    - 양쪽 DB를 주기적으로 대조하는 **Reconciliation** 도 둡니다.

## 재화 차감 후 지급 전 Crash (Q21)
- 로그 상태가 `Paid`에서 멈춘 거래가 되므로, 복구 시 이를 찾아 지급을 완료합니다.

1. 재화 차감과 `Paid` 기록을 같은 DB 트랜잭션으로 커밋했기 때문에, **차감됐는데 기록이 없는 상태는 존재하지 않습니다.**
2. 서버 재시작 시(또는 주기적 배치가) `Paid`에 머물러 있는 거래를 조회해 지급을 재시도합니다.
3. 지급 단계는 `TransactionID`로 멱등해서, 지급은 됐는데 상태 갱신 전에 죽은 경우에도 중복 지급이 없습니다.
4. 인벤토리가 가득 찼거나 캐릭터가 오프라인이면 **우편함(지급 대기함)** 으로 보냅니다. 거래소 지급을 처음부터 우편으로 하면 이 문제가 단순해집니다.
5. 재시도해도 실패하면 재화를 환불하는 보상 트랜잭션을 수행하고, 전 과정을 로그로 남겨 CS 대응이 가능하게 합니다.

> 핵심 문장: "재화와 아이템을 한 트랜잭션으로 묶을 수 없다면, 각 단계를 기록과 함께 커밋하고 멱등하게 만들어, 어느 지점에서 죽어도 로그를 보고 이어서 진행할 수 있게 합니다."

## 동시 구매 처리 (Q19)
- 매물 상태의 **단일 소유자 (Single Source of Truth)** 를 거래소 서버/DB로 둡니다.
- 같은 매물을 여러 명이 동시에 사려 할 때는 **조건부 UPDATE** 로 한 명만 성공시킵니다.

```sql
UPDATE dbo.Listing
SET    State = 'Reserved', BuyerID = @BuyerID
WHERE  ListingID = @ListingID AND State = 'OnSale';

IF @@ROWCOUNT = 0
    RETURN -1; -- 이미 팔렸거나 예약됨
```
- 또는 버전 컬럼으로 **낙관적 락 (Optimistic Lock)** 을 겁니다.
- 목록 조회는 캐시(Redis 등)나 읽기 복제본에서 처리하고, 구매 시점에만 원본에서 재검증합니다.

## 2PC vs Saga
|항목|2PC|Saga|
|---|---|---|
|일관성|강한 일관성|최종 일관성|
|락 유지|전체 완료까지|각 로컬 트랜잭션 동안만|
|장애 시|코디네이터 장애 시 blocking|재시도/보상으로 복구|
|구현 난이도|인프라 의존|상태 머신, 멱등성 직접 설계|
|게임 서버 적합성|낮음|높음|
