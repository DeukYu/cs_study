# unordered_map (Hash Table)
> 📌 기출: [NC Project NL Q9, Q12, Q15](../Interview/NC_Project_NL_%EB%A9%B4%EC%A0%91_%EC%A7%88%EB%AC%B8.md) - unordered_map의 내부 데이터 관리 / vector와 다른 문제 / 데이터를 찾아가는 과정

- **해시 테이블** 기반의 key-value 컨테이너
- 평균 O(1) 검색/삽입/삭제, 순서는 보장하지 않습니다.

---

## 내부 구조 (Q9)
- **버킷 배열 + 체이닝 (Separate Chaining)** 방식
- 표준이 노드 포인터/참조 안정성을 요구하기 때문에, 원소는 **개별 할당된 노드** 로 저장됩니다.

```
buckets
┌───┐
│ 0 │ ──▶ [k1|v1] ──▶ [k7|v7]
├───┤
│ 1 │ ──▶ (empty)
├───┤
│ 2 │ ──▶ [k3|v3]
├───┤
│ 3 │ ──▶ [k4|v4] ──▶ [k9|v9] ──▶ [k2|v2]
└───┘
```

- **구현 차이**
    - MSVC: 모든 원소를 하나의 `list`로 연결하고, 버킷은 그 list 내 구간의 시작/끝 반복자를 들고 있습니다.
    - GCC: 단일 연결 리스트 + 버킷이 "이전 노드"를 가리키는 구조입니다.

### Rehash
- `load_factor`(원소 수 / 버킷 수)가 `max_load_factor`(기본 1.0)를 넘으면 버킷 수를 늘리고 **전체를 rehash** 합니다.
- 이때 **반복자는 무효화** 되지만, 노드는 그대로라 **원소 참조/포인터는 유지** 됩니다.
- 최악의 경우 해시 충돌로 한 버킷에 몰리면 O(n)입니다.

## 데이터를 찾아가는 과정 (Q15)
1. key를 **hash 함수** 에 넣어 `size_t` 해시값을 구합니다.
2. **버킷 인덱스** 로 변환합니다.
    - GCC: 소수 크기 버킷에 `hash % bucket_count`
    - MSVC: 2의 거듭제곱 크기에 `hash & (n - 1)`
3. 해당 버킷의 **노드 체인** 을 따라가며 각 노드의 key와 `operator==`로 비교합니다. (구현에 따라 저장된 해시값을 먼저 비교)
4. 일치하면 해당 노드의 반복자를, 끝까지 없으면 `end()`를 반환합니다.

- **설명 포인트**: 해시 계산 + 버킷 접근 + 노드 포인터 추적 때문에 캐시 미스가 최소 1~2번 생깁니다. O(1)이어도 원소가 적으면 vector 선형 탐색보다 느릴 수 있고, 문자열 키는 해시 계산 비용도 큽니다.

## vector와 다르게 발생하는 문제 (Q12)
1. **잦은 작은 할당**: 원소마다 노드를 new/delete → 할당 비용, 힙 락 경합, 단편화 ([list](./list.md)와 동일)
2. **Rehash 스파이크**: 일시에 전체를 재배치해 순간 지연이 생기고 반복자가 무효화됩니다.
3. **해시 충돌**: 해시 함수가 나쁘면 한 버킷에 쏠려 O(n)으로 떨어집니다.
4. **Hash DoS**: 외부 입력(유저가 보낸 문자열 등)을 키로 쓰면, 의도적으로 충돌을 일으키는 공격 대상이 됩니다.

### 대응
- `reserve()`로 버킷을 미리 확보해 rehash 방지
- 노드 풀 / 전용 Allocator
- 성능이 중요하면 **open addressing** 해시맵으로 교체 (abseil `flat_hash_map`, robin hood hashing 등)
    - 원소를 버킷 배열에 직접 저장해 캐시 효율이 좋지만, 포인터 안정성은 없습니다.
