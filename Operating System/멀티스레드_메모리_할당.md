# 멀티스레드 환경의 메모리 할당
> 📌 기출: [NC Project NL Q13, Q14](../Interview/NC_Project_NL_%EB%A9%B4%EC%A0%91_%EC%A7%88%EB%AC%B8.md) - 멀티스레드 환경에서 new/delete가 반복될 경우 어떤 문제가 발생하고, 병목은 어떻게 해결하는가?

- 기본 힙은 프로세스 전체가 공유하는 자원이라, 여러 스레드가 동시에 `new`/`delete`를 반복하면 동기화 비용과 단편화 문제가 생깁니다.

---

## 발생하는 문제
1. **힙 락 경합**
    - 스레드들이 동시에 할당하면 힙 락을 두고 대기하고, 커널 대기로 빠지면 Context Switching까지 발생해 스케일이 안 됩니다.
    - Windows는 LFH(Low Fragmentation Heap)로 많이 개선됐지만 완전하지 않습니다.

2. **단편화 (Fragmentation)**
    - 크기가 다양한 블록이 섞여 장기 구동 서버의 메모리 사용량이 점점 부풀고, 큰 할당이 실패할 수 있습니다.

3. **False Sharing**
    - 서로 다른 스레드가 쓰는 작은 객체가 같은 캐시라인에 배치될 수 있습니다.

4. **시스템 콜과 Page Fault**
    - 힙이 커지거나 줄어들 때 OS 호출(`VirtualAlloc` 등)과 Page Fault가 동반됩니다.

5. **교차 스레드 해제**
    - 네트워크 스레드가 만든 패킷을 로직 스레드가 해제하는 패턴은 스레드 로컬 처리를 무력화해 더 비쌉니다.

---

## 해결 방법
> 먼저 프로파일러(VTune, Superluminal, ETW/WPA)로 락 대기가 정말 할당자에서 나오는지 확인합니다.

1. **할당 자체를 줄이기**
    - `reserve`, 객체 재사용, 스택/임시 버퍼 활용, 값 타입 사용

2. **메모리 풀 (Object Pool)**
    - 자주 쓰는 고정 크기 객체(패킷 버퍼, 세션, 아이템)는 미리 덩어리로 잡아 free-list로 관리합니다.
    - 크기가 다양하면 크기 클래스(size class)별 풀을 둡니다.

3. **스레드 로컬 캐시 (TLS)**
    - 풀을 스레드별로 두어 락 없이 할당합니다.
    - 남거나 부족할 때만 묶음 단위로 전역 풀과 교환합니다. 전역 풀은 lock-free 스택(`SLIST`)이나 짧은 SpinLock으로 보호합니다.

4. **검증된 할당자로 교체**
    - tcmalloc, jemalloc, mimalloc은 이미 스레드 캐시 구조라, 전역 `operator new`만 바꿔도 큰 효과가 있습니다.

5. **구조 변경**
    - 틱/요청 단위 임시 데이터는 **Arena(Linear) 할당자** 로 포인터만 올리다가 한 번에 리셋합니다.
    - 스레드 간 할당/해제가 엇갈리지 않도록 소유권을 정리합니다.

|방법|장점|단점|
|---|---|---|
|메모리 풀|할당 O(1), 단편화 없음|고정 크기 위주, 메모리 선점|
|TLS 캐시|락 없음|스레드 간 불균형 처리 필요|
|tcmalloc 등|적용이 쉬움|외부 의존성, 튜닝 필요|
|Arena|가장 빠름, 일괄 해제|개별 해제 불가|
