# Atomic 연산과 캐시 일관성
> 📌 기출: [NC Project NL Q5](../Interview/NC_Project_NL_%EB%A9%B4%EC%A0%91_%EC%A7%88%EB%AC%B8.md) - atomic<int32_t>에 32개 스레드가 무한히 fetch_add(1)하면 CPU에서는 어떤 일이 벌어지는가?

- **결론**: 결과값은 정확하지만, **캐시라인 하나를 32개 코어가 번갈아 독점** 하면서 연산이 사실상 한 줄로 직렬화됩니다. CPU 사용률은 100%인데 전체 처리량은 스레드 수와 무관하게 일정하거나 오히려 떨어집니다.
- 아래 지연 시간/처리량 수치는 CPU 세대와 구성에 따라 달라지는 **대략적인 크기** 입니다.

---

## 1. 어떤 명령어로 컴파일되는가
```cpp
counter.fetch_add(1);   // 기본값 memory_order_seq_cst
```

|아키텍처|생성 명령어|특징|
|---|---|---|
|x86-64|`lock xadd [mem], reg`|명령어 하나로 RMW(읽기-수정-쓰기) 완료. 항상 한 번에 성공|
|ARMv8.1+ (LSE)|`ldaddal`|명령어 하나. L3나 원격 노드에서 대신 실행될 수도 있음 (far atomic)|
|ARMv8.0|`ldaxr` / `stlxr` 루프 (LL/SC)|다른 코어가 끼어들면 `stlxr` 실패 후 재시도. 경합이 심하면 재시도 폭증|

- x86의 `lock xadd`는 실패나 재시도가 없으므로, 이 질문은 순수하게 **캐시라인 쟁탈 비용** 을 묻는 질문입니다.

---

## 2. lock 접두사가 원자성을 보장하는 방법
- 예전 CPU는 `LOCK#` 신호로 **메모리 버스 전체** 를 잠갔지만, 지금은 **캐시라인 하나만** 잠급니다 (cache locking).

1. 코어가 해당 캐시라인을 자기 L1에 **Modified / Exclusive** 상태로 가져옵니다. (쓰려면 독점권이 필요)
2. RMW가 끝날 때까지 그 라인에 대한 다른 코어의 요청(snoop)에 **응답을 미룹니다.** 이것이 원자성의 실체입니다.
3. 연산이 끝나면 미뤄둔 요청에 응답하고 라인을 넘겨줍니다.

### Split Lock
- 변수가 **캐시라인 경계(64B)에 걸쳐 있으면** 캐시 락을 쓸 수 없어 **버스 전체를 잠급니다.**
- 수백~수천 사이클이 걸리고 다른 모든 코어의 메모리 접근까지 멈추게 해서, 최근 Intel/Linux는 이를 감지해 경고하거나 차단합니다.
- `std::atomic`은 정렬을 보장하므로 안전하지만, `#pragma pack`된 구조체 안의 정수를 `InterlockedIncrement`로 다루면 실제로 발생할 수 있습니다. ([메모리_얼라인먼트](./%EB%A9%94%EB%AA%A8%EB%A6%AC_%EC%96%BC%EB%9D%BC%EC%9D%B8%EB%A8%BC%ED%8A%B8.md))

## 3. 캐시 일관성 프로토콜 (MESI)
- 코어마다 L1/L2가 따로 있고, 이들의 일관성을 MESI 계열 프로토콜이 맞춥니다. (Intel은 MESIF, AMD는 MOESI)

|상태|의미|
|---|---|
|Modified|이 코어만 가진 수정된 데이터 (메모리와 다름)|
|Exclusive|이 코어만 가진 깨끗한 데이터|
|Shared|여러 코어가 읽기 전용으로 공유|
|Invalid|무효화된 사본|

### 증가 한 번마다 일어나는 일
- 코어 B가 증가시키려는데 라인이 코어 A에 M 상태로 있다면

```
코어 B: L1 miss → RFO(Read For Ownership) 요청 발행
          │
          ▼
   L3 / Snoop Filter (Home Agent): "이 라인은 A가 갖고 있음"
          │
          ▼
코어 A: (진행 중인 lock xadd 완료까지 대기) → 사본 Invalidate, 최신 값을 B로 전달
          │
          ▼
코어 B: 라인을 M 상태로 받아 xadd 실행 → 이제 B가 소유자
```

- 이 과정이 **증가 한 번마다** 반복됩니다. 라인이 코어 사이를 계속 돌아다니는 현상을 **Cache Line Ping-Pong** 이라고 합니다.

|상황|연산 1회 비용 (대략)|
|---|---|
|경합 없음 (라인이 내 L1에 M 상태)|~20 사이클 (수 ns)|
|같은 소켓 내 경합|수십 ns (코어 간 전송)|
|소켓 간 경합 (멀티소켓)|100 ~ 수백 ns|

- AMD처럼 CCX/CCD로 나뉜 구조는 같은 CCX 안에서는 싸고, 다른 CCX로 넘어가면 비쌉니다.
- **어느 순간이든 라인을 가진 코어는 하나뿐** 이므로, 전체 처리량은 "라인 한 번 넘기는 시간"이 결정합니다.

## 4. 스레드 수에 따른 처리량
```
전체 처리량
   ▲
   │█
   │█
   │█ ▄
   │█ █ ▃ ▂ ▂ ▂ ▂ ▂      ← 늘지 않고, 오히려 줄어듦
   └──────────────────▶ 스레드 수
    1 2 4 8 16 24 32
```
- **1개**: 라인이 L1에 머물러 가장 빠름 (초당 수억 회 수준)
- **2개 이상**: 매번 라인 이동이 끼어들어 **전체 처리량이 오히려 감소**
- **그 이후**: 대략 일정하거나 조금씩 감소 (요청이 몰리면서 큐잉 지연과 snoop 트래픽 증가)
- 스레드 하나당 처리량은 `전체 ÷ 32`로 쪼그라듭니다.

## 5. 코어 내부: CPU 100%인데 일을 안 하는 이유
- `lock` 명령은 **풀 메모리 배리어** 입니다.
    - 실행 전에 **스토어 버퍼를 전부 비워야** 합니다.
    - 뒤에 오는 load가 앞질러 실행될 수 없습니다.
    - 비순차 실행(out-of-order)의 이점이 사라지고, 파이프라인은 RFO 응답을 기다리며 멈춥니다 (stall).
- OS가 보기에는 쉬지 않고 실행 중이라 **CPU 사용률 100%** 지만, 하드웨어 카운터로 보면 **IPC가 바닥** 이고 대부분 메모리 대기 사이클입니다.
- "100% 바쁜데 느린 서버"의 전형적인 패턴입니다.

---

## 6. 주변에 미치는 영향
- **인터커넥트 포화**: RFO, invalidate, 데이터 전달 메시지가 링 버스/메시/Infinity Fabric을 계속 채워, **이 카운터와 상관없는 다른 스레드의 메모리 접근까지 느려집니다.**
- **False Sharing 전염**: 같은 64B 라인에 다른 변수가 있으면, 그 변수를 읽기만 하는 스레드도 매번 캐시 미스를 맞습니다. 카운터를 `alignas(64)`로 고립시켜야 하는 이유입니다.
- **하이퍼스레딩**: 32스레드가 16코어 × 2 SMT라면, 같은 물리 코어의 두 스레드는 L1을 공유해 서로 넘기는 비용은 싸지만, 실행 자원을 나눠 쓰므로 이득이 크지 않습니다.
- **전력/클럭**: 전 코어 풀로드로 터보 클럭이 내려갈 수 있습니다.

## 7. 공정성과 OS 스케줄링
- **불공정 분배**: 하드웨어는 코어 간 공정성을 보장하지 않습니다. 방금 라인을 받은 코어가 몇 번 연속 증가시키거나, 토폴로지상 가까운 코어끼리 라인을 더 자주 주고받습니다. 스레드별 증가 횟수를 세어보면 꽤 차이가 납니다.
- **선점돼도 문제없음**: 스레드가 코어보다 많아 OS가 선점해도, atomic은 lock-free라 다른 스레드는 계속 진행합니다. 스핀락이라면 락을 쥔 스레드가 선점되는 순간 나머지가 전부 헛돕니다.
- **Context Switching은 없음**: 블로킹이 없기 때문입니다. "mutex보다는 낫지만 확장되지 않는다"가 정확한 표현입니다.

## 8. 오버플로우가 생각보다 빨리 온다
- `int32_t` 최댓값은 약 21억(2³¹)입니다.
- 경합 상태 전체 처리량을 초당 수천만 회로 잡으면 **수십 초~몇 분 안에** 오버플로우가 납니다.
- `std::atomic`의 부호 있는 정수 연산은 표준상 **2의 보수로 정의되어 UB가 아닙니다.** `INT_MIN`으로 감길 뿐입니다.
- 하지만 로직상 버그이므로, ID 발급기나 통계 카운터는 `int64_t` / `uint64_t`를 사용합니다.

---

## 9. 방식별 비교
|방식|경합 시 동작|확장성|
|---|---|---|
|`mutex` + `++`|커널 대기, Context Switching|가장 나쁨|
|CAS 루프 (`compare_exchange`)|실패하면 라인을 다시 받아 재시도, 낭비 큼|나쁨|
|`fetch_add` (`lock xadd`)|항상 한 번에 성공, 라인 이동 비용만|경합 원자 연산 중 최선이지만 확장 안 됨|
|스레드별 카운터 + 합산|공유 쓰기 없음|코어 수에 비례해 확장|

### 해결책: 스레드별 카운터
```cpp
struct alignas(64) PaddedCounter {
    std::atomic<int64_t> v{0};
};
PaddedCounter local[32];   // 스레드마다 다른 캐시라인

void Inc(int tid) {
    local[tid].v.fetch_add(1, std::memory_order_relaxed);
}

int64_t Total() {          // 읽을 때만 합산
    int64_t s = 0;
    for (auto& c : local) s += c.v.load(std::memory_order_relaxed);
    return s;
}
```
- 여전히 `fetch_add`지만, 라인을 가진 코어가 하나뿐이라 **L1 안에서 끝납니다.**
- x86에서는 `relaxed`여도 `lock` 명령은 그대로 나오므로, 이득은 순서 제약보다 **캐시라인 분리** 에서 나옵니다.
- 더 줄이려면 스레드 로컬 일반 변수에 모았다가 N번에 한 번만 공유 카운터에 더합니다 (**배칭**).

## 10. 직접 확인하는 방법
- **Linux**: `perf c2c record` / `perf c2c report` → 캐시라인 경합(**HITM**: 다른 코어의 Modified 라인을 가져온 횟수)이 어느 라인/코드에서 나오는지 확인
- **Windows**: Intel VTune의 Memory Access / Microarchitecture Exploration 분석으로 contested access 확인
- **간단 실험**: 스레드 수를 1, 2, 4, 8, 16, 32로 늘리며 1초간 전체 증가 횟수를 측정하면 4번의 그래프가 재현됩니다.

## 면접 30초 답변
> "`lock xadd` 한 명령으로 처리되기 때문에 값은 정확합니다. 다만 쓰기를 하려면 캐시라인을 MESI의 Modified 상태로 독점해야 해서, 32개 코어가 라인 하나를 번갈아 가져가는 Ping-Pong이 일어납니다. 연산 하나가 L1 지연이 아니라 코어 간 전송 지연이 되고, lock 명령은 풀 배리어라 파이프라인도 멈춥니다. 그래서 CPU는 100%인데 전체 처리량은 스레드 수와 상관없이 일정하거나 오히려 떨어집니다. 해결책은 `alignas(64)`로 분리한 스레드별 카운터를 두고 읽을 때 합산하는 것이고, int32는 이 속도면 금방 오버플로우가 나니 64비트를 써야 합니다."
